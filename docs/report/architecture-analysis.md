# 多智能体办公系统体系结构分析

本分析对应multi-agent-office-lab的实际实现，以LangGraph集中编排、Pydantic契约、本地确定性数据工具及Streamlit工作台为对象。v1.0是在v0.6功能基线上完成可复现交付，不把参考指导书中的OpenClaw组件宣称为已经安装，也不把五个角色宣称为五个独立分布式服务。分析依据为workflow.py、agent_schemas.py、workflow_schemas.py、agent_runtime.py、agents/、tools/、workflow_export.py、web_runtime.py与各版验证记录。

## 一、架构目标与集中控制的取舍

系统要解决的是一个边界清楚的办公任务：给定部门、期间、报告结构和三个数据文件，生成有统计依据且经过审核的工作报告。核心质量目标是事实可核对、流程有界、错误可见、产物不混淆和别人能复现。课程原型的工作量与数据规模有限，因此采用单进程集中控制，优先让每一步输入输出和终止原因可检查，而不是先引入分布式部署复杂度。

LangGraph的图抽象以状态、节点和边组织执行，条件边可表达不同路径，概念见[官方图API文档](https://docs.langchain.com/oss/python/langgraph/graph-api)。本项目不只是按名字顺序调用函数：workflow.py维护实际WorkflowState，需求、大纲、权威统计、草稿和审核在节点执行后进入共享状态，下一个节点消费前一个节点的真实输出。Manager至Writer之间的条件边检查status，只有running才继续；Checker决定完成、需要材料、继续返工或最终拒绝。因此调用失败或材料不足能够停止下游，不会用固定样例填补一个缺失节点。

集中状态的优点是一次工作流可以共用预算与审计记录，检查来源和当前草稿也不需要跨服务一致性协调。代价是调度器成为共同故障边界，进程退出会失去内存任务，当前实现没有持久检查点和重启恢复。不能因为使用了多智能体框架就推断已具备分布式容错。对于本项目，清晰可重复的本地行为比增加服务器数量更重要；如扩大到多用户长期任务，则需要改变这个取舍。

## 二、角色分工与通信契约

五个角色体现的是五种决策责任，而不是五份完全隔离的模型。Manager确认需求有原文依据，Planner组织章节并安排四个指标唯一归属，Data申请授权工具并总结工具结果，Writer形成结构化草稿，Checker审核实际草稿。角色可以共用同一兼容模型服务，但具有不同输入、提示和输出契约；单次任务专用AgentSession避免预算与事件混入其他运行。

通信通过类型化状态完成。Requirements继承DataRequest，明确部门、开始日期、结束日期、来源声明及必需章节；Outline包含可唯一标识的章节和指标归属；DataResult包含统计口径、来源及异常；Draft把正文、FactClaim和Suggestion分开；Review同时携带passed、issues、revision_instructions和needs_input。ContractModel禁止额外字段，日期要求严格ISO格式、起止顺序合法，事实声明拒绝布尔型伪装数字和非有限值。结构化解析还拒绝重复JSON键，防止同一字段存在多个相互矛盾值。

这种接口相当于角色之间的显式协议。它让模型文本的不确定性尽早进入可检查边界，减少“上一步说得似乎合理，下一个角色自行猜测”的传播。契约只负责形式和部分跨字段不变量，并不能自动证明业务事实正确。因此还需要数据工具、需求原文校验、Checker程序规则和最后导出门禁，不能将Pydantic解析成功等同于报告可信。

节点输入和结果使用深拷贝保存审计快照。Writer拿到的是权威统计副本，不能通过修改该副本改变共享事实；返工仍使用相同需求、大纲和DataResult。若模型试图把项目总数从3改成4，Checker的fact_value校验会拒绝，而不是修改数据配合草稿。集中状态并不意味着所有组件都能随意写所有字段，职责边界由接口和执行代码共同维持。

## 三、模型推理与规则计算的组合

系统将容易歧义的语言任务交给模型，将可精确定义的统计任务交给程序。部门和季度需求由Manager解析，但要核对用户原文；项目快照筛选、去重、状态判断、完成率及成果数量由tools计算。模型不重新计算指标，不把数据摘要作为权威值。Data Agent确实进行工具往返：先得到模型的function call，程序校验后执行一次run_data_tools，再把精简结果回传用于总结。

工具授权具有两层边界。模型只能请求注册名run_data_tools，并且必须只有一次调用；参数集合仅允许department、start_date、end_date，且必须严格等于调用方授权值。数据路径由CLI或网页后台绑定，不接受模型指定。因此不能通过提示词让Data读取任意服务器路径。网页上传先校验固定文件名、文件大小、编码及全部业务记录，失败在模型创建前终止。数据内容被声明为信息而不是指令，但这一提示本身不是完备的注入防护；白名单和参数对照才是实际代码约束。

统计语义经过独立手算固定：同一期间按每个项目最新快照计算项目数，completed计入完成数，开始日期含、结束日期不含；无分母返回null。数据全量验证覆盖筛选范围外异常，避免以“此次统计没用到”掩盖输入损坏。来源SHA256绑定实际字节，物理行号定位所选事实；这提高了追踪能力，但没有签名或外部可信时间戳，不能宣称具有对抗性不可篡改审计。

## 四、审核不是一个布尔按钮

Checker采用程序规则优先、模型判断补充。程序检查章节、指标完整性、值、单位、来源、归属以及固定渲染结果；已知错误无需再次请求模型判断。模型审核在本地检查通过后关注逻辑、表达及建议，不能覆盖程序发现的错误。导出阶段再次从完整WorkflowResult核对历史与当前草稿，避免把内部的passed字段直接当作可下载权限。

这一设计来自真实问题。v0.4真实联调中四项指标正确，但自由正文出现无材料支持的“按计划推进”和“资源分配紧张”，Checker仍通过。项目没有把这一结果改写成全部可靠，而是保留失败边界，并在v0.5采用constrained正文。章节说明必须逐字符合允许的范围模板，四项数值由FactClaim核对后固定渲染；未来行动列为Suggestion，不能写成已发生事实。约束牺牲了一部分开放叙述能力，却使核心报告更容易检验。它仍不是通用自然语言事实验证，建议可行性和未建模业务知识需要人类判断。

最终report.md要求completed且最后审核、逐轮历史、节点结果、权威数据及实际请求账本一致。未审核的新草稿可以保存，不能伪造该轮review.json；导出拒绝保留实际记录，不应变成展示成功。网页还要求核心结果与任务快照都completed且门禁产物确实存在，避免核心图结束后文件保存失败仍显示可交付报告。

## 五、调度、有界返工与故障成本

Checker拒绝且材料完整时，调度器将上一实际Draft和Review传给Writer，同时保留需求、大纲、指标和来源。首次生成为第0轮，之后最多开始第1、2轮返工。revision_count在路由到Writer时增加，表示已经开始的修改尝试；若该Writer失败，也不能把次数回退。持续错误达到上限为review_failed，材料不足为needs_input，模型、解析、工具、预算或导出异常为failed。

业务返工和网络重试是不同恢复机制。返工重新组织报告内容并再审核；网络重试只重发同一个模型请求，不能隐式重跑整张图。AgentSession默认retry_budget=0，允许时每逻辑请求最多重试一次、会话最多两次，只针对指定连接/超时、429、5xx类别；鉴权或不合法结构不靠无限重试解决。适配器内部重试固定为零，避免外层账本看见一次而底层发送多次。

每次HTTP之前同时检查请求数和输出预留额度，失败尝试也进入账本。正常链路6请求，Data占两次；两次业务返工最多再加4请求。若另外允许两个Writer重试，硬上限12次HTTP和5568输出预留。实际服务usage、输出预留和逻辑调用数分别保存，不能把预留上限当成费用，也不能把null的usage写成零。这样的成本模型对昂贵且不确定的模型任务很重要：故障路径同样有可预测上界。

## 六、网页层的并发与一致性边界

Streamlit页面可能因交互重复运行，因此UI不直接创建模型Client执行长任务。每个会话的session_state保存RunController，其start方法在锁内完成一次任务接纳；任何已接纳任务都需要终态reset后才能再开始。输入在接纳时冻结为不可变文件字节与复制选项，后台线程写入隔离临时目录并执行原图，结束后清理。下载返回已有白名单产物bytes，而不接受页面输入的服务器路径。

网页状态片段定期读取深拷贝快照，轮询本身不产生模型请求。node_started在角色动作之前通知观察者，使界面能显示实际正在运行角色；HTTP和工具内部事件在角色结束后公开。页面不能据此宣称逐token流式可观测，也不使用计时器伪造角色进度。观察者得到事件副本，抛异常不会改变原工作流账本或触发已接纳请求重放。

CSV解析使用进程全局字段大小设置，为防止多个预检互相改变限制，将修改、解析、恢复区域加锁；这个锁不把全部模型请求全局串行。不同会话仍使用不同Session、UUID、数据目录和快照。当前防重是同一控制器内保证，不覆盖新浏览器会话、服务重启或多进程部署。需要生产幂等时应加入稳定任务键、持久接纳记录和队列事务，而不能仅依赖内存锁。

## 七、与参考框架概念及传统多智能体方式的比较

参考指导书使用Gateway、Agent、Skills、Tools等概念。这里可作职责映射：CLI与Streamlit是请求入口，workflow.py是集中调度，agents/是角色行为，工具注册与角色函数承载受限能力，tools/是确定性操作。但这些只是本项目的架构职责对应，不代表使用了OpenClaw网关协议、其Agent基类或Skills运行时。教师允许更换开源框架，因此比较重点应是相同办公任务怎样保持职责和可核对消息，而非复制参考安装命令。

JADE官方说明采用FIPA ACL消息，提供AMS/DF服务，容器在JVM中运行，Agent拥有私有入站消息队列，见[官方技术说明](https://jade.tilab.com/technical-description/)。本项目没有使用这些协议或服务，以下是结合这些特征对架构取舍的分析。

与这类基于独立Agent和消息通信的传统MAS设计相比，本项目不强调每个角色拥有独立地址、自治生命周期或异步协商协议。控制策略由显式图固定，Agent的语言决策来自LLM，通信采用共享状态和结构化契约。消息驱动方式可能更适合异构节点自治、去中心协商和长期运行，但需要解决消息重复、顺序、超时、权限及跨节点一致性；本项目便于端到端追踪和教学演示，角色自治与水平扩展较有限。这里是架构范式比较，未实际安装或基准测试JADE，不能据此作性能优劣结论。

也不能把LLM-Agent简单理解为传统规则角色换了一个名字。模型输出具有语言弹性和随机风险，故要在角色边界进行JSON校验、预算控制与事实门禁；传统确定性组件同样需要错误处理，但这里额外存在幻觉和提示影响。项目以LLM提供语义能力、确定性程序提供事实与控制，把两者职责相接，体现可审查而非无限自主的多智能体协作。

## 八、演进方向与验证策略

扩展数据源前应先设计字段、业务口径、来源和无数据含义，再注册工具；增加角色前应明确新节点需要的状态字段、可写范围、失败类别、预算与导出条件。若引入数据库或外部写操作，应增加用户权限、人工审批与副作用幂等，不能沿用当前只读统计的假设。分布式部署还需持久任务、跨进程调度、共享预算和日志追踪，工作流接口可以保留，但恢复和接纳层需升级。

验证分为单元契约、HTTP级独立集成、实际图及故障注入、网页原生交互和GitHub新克隆。offline_mock只替换模型HTTP响应，其余图、数据、程序审核和文件导出实际执行；这有助于低成本、确定性地覆盖失败分支，但不证明真实模型质量。历史DeepSeek实测按原版本保存，v1.0不为截图重复付费调用。预期失败必须验证没有最终报告、正确停点与次数上限，不能把所有异常都当成“通过”。

当前体系结构的主要价值在于把需求、事实、生成、审核和交付联系为一条有证据的路径。它没有实现无限自治、任意文档理解或生产级分布式恢复；其可靠性来自明确范围、类型契约、有限资源和多层门禁。架构分析应承认这些限制，并将后续扩展建立在实际验证过的控制边界上。
