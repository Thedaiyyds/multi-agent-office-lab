# 报告与审核接口草案

本文件是 v0.3～v0.6 的接口设计草案。v0.1 不实现 Writer、Checker、报告导出或网页界面；以下字段将在实现前与共享模型及 [数据接口](data-contract.md) 核对，不视为已存在的 Python 类型。

## 输入边界

Writer 接收 `run_id`、需求、大纲、数据结果和上一轮审核意见。需求包括部门、日期半开区间 `[start_date, end_date)`、必需章节和输出格式；大纲提供稳定章节编号。数据结果由角色 B 产生，指标包含稳定 ID、值、单位、统计口径和来源标识。

Writer 与 Checker 不修改原始数据、指标、口径和来源。无数据或缺失值由数据模块明确表示，正文说明缺失，不补造数值。是否可继续由编排层处理。

## Writer 输出 Draft

| 字段 | 含义 |
| --- | --- |
| `run_id` | 当前运行编号 |
| `markdown` | 报告正文 |
| `fact_claims` | 可核对的核心事实声明，包含 `section_id`、`metric_id`、`value`、`source_ids` |
| `suggestions` | 后续计划或建议，标明所属章节，区别于已发生事实 |

数值展示遵循统一精度规则。无定义的比例不显示为 0%。正文中的核心统计数字采用约定模板或明确解析规则，使程序有可检查的范围。修订版本保持同一个 `run_id`，由编排层记录轮次。

## Checker 输出 Review

| 字段 | 含义 |
| --- | --- |
| `passed` | 是否通过当前规则和模型审核 |
| `issues` | 问题列表，每项包括问题类型、章节/字段位置、实际值、期望依据和严重程度 |
| `revision_instructions` | 面向 Writer 的具体修改动作 |
| `needs_input` | 是否存在不能通过改写解决的关键数据缺失 |

程序检查必需章节和结构化核心事实，模型检查逻辑、内容覆盖与表达。通过检查不代表保证所有自然语言事实正确；验收报告说明实际覆盖范围。

## 编排与导出

审核通过后，编排层进入 `completed`，导出该运行的 Markdown。可修正问题返回 Writer；首次草稿之后最多修改两次，每次修改后复核。关键数据缺失进入 `needs_input`；达到上限仍未通过进入 `review_failed`，保留草稿及意见。调用错误进入 `failed`，与审核不通过区分。

导出按 `run_id` 隔离目录，避免覆盖。仅审核通过的产物标为最终报告，其他内容明确标注草稿或审核未通过。UI 下载对应当前运行和审核轮次的实际产物。

## 界面与证据约定

角色 A 提供统一运行入口及事件：运行编号、时间、角色、事件类型、状态、耗时与脱敏摘要。角色 C 订阅这些实际事件更新界面，不使用计时动画冒充执行进度，不自行复制编排逻辑。

后续验收包括：错数字/缺章节的明确错误注入可被定位和修订，永久失败在上限处终止；网页重复点击不重复提交，下载内容与运行编号相符。截图记录 `run_id`、commit SHA、输入场景及结果，mock、注入错误与真实模型分别标注。
