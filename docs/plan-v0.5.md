# v0.5 详细开发计划

基线 v0.4.0，main `0c4c9a101608110dc75bbe1427a5da2e62f865ee`。分支 `feature/v0.5-revisions`；最终提交独立 PR，CI 与交叉审查通过后 merge，发布 v0.5.0 标签。开发者仍为一人，A/B/C 表示实际 AI 协助角色。

## 目标与设计决定

1. 真正实现 Checker → Writer → Checker 条件循环。首次草稿为 revision_index=0，之后最多修改两次，revision_count 只计已开始的业务返工尝试（路由到下一 Writer 时递增，失败的返工尝试也计入）；需求、数据、来源与统计值在所有轮次保持不变。
2. 正常通过 → completed；缺关键材料 → needs_input；可修正问题且有额度 → Writer；达到两次修改上限仍拒绝 → review_failed；请求、解析、工具或预算失败 → failed。所有非成功状态不导出 report.md。
3. 为避免 v0.4 实际“资源紧张”等无依据正文被 Checker 放过，完整工作流启用 constrained 正文：各章使用明确给定、无数字的事实范围说明，所有核心数值从结构化 fact_claims 受约束模板渲染，再与 metrics 核对。Writer 返回不允许的正文，即使模型审核通过也拒绝并返工。不静默纠正模型结果。
4. 模型仍负责事实归属、结构化报告与后续建议。建议明确标为尚未实施、待人工评估，不是历史事实。约束牺牲部分自由表达以便校验；不声称所有建议可行或实现通用自然语言事实验证。独立 agent-demo 的兼容 freeform 样例与完整 run 的约束要明确区分。
5. 已知程序错误先返回程序审核意见，省去无必要的 Checker 模型调用；通过程序检查后才进行模型表达/建议审核。日志分别标明 program_only / program_and_model。
6. 网络重试与业务修改分开。每个模型请求最多重试一次，全会话最多两次；仅超时、连接异常、429/5xx 可重试。鉴权、参数、非法 JSON/结构及本地校验不自动重试。默认 retry_budget=0，需显式启用；每个 HTTP 尝试均计入总请求和输出预留预算。未知用量保留 null。

## 预算和实验约定

- 正常完整链路 6 个逻辑模型请求，上限两次修改时至多 10 个逻辑请求；程序审核发现错误时 Checker 可不调用模型，因此实际可能更少。每轮 Writer 768、Checker 256，基础输出预留最多 4032 tokens；输入另计。
- 可选 retry_budget 为 0/1/2，每个逻辑请求最多一次网络重试。总请求硬上限 12，输出预留硬上限 5568；CLI 可进一步下调。真实验收优先限制为 7～8 次 HTTP、最多 3008 预留输出、零网络重试、DeepSeek thinking disabled。失败不自动重复整次实测，先离线排查。
- workflow-test 是独立故障实验入口，case bad-fact / missing-section 仅首次注入，always-bad 每轮持续注入。normal run 不注入。记录实验标记、原 Writer 生成结果和注入后草稿，不能将人工注入冒充模型自然犯错。live 注入须显式选择，与正常业务运行分开。
- 同一 run_id 保存所有 nodes/events，revision_history 及 revisions/00～02/draft.md、review.json；最终 draft.md 是最新草稿，成功才生成 report.md。中途失败保留先前已审核草稿和实际失败节点。
- 架构/时序图必须反映当前条件循环及终态。没有实际捕获的截图不能以日志或模拟图替代；截图与最终实验报告要求继续保留。

具体测试数量、真实请求与 token 用量、代码 SHA、审查结果及发布状态在 validation-v0.5.md / review-v0.5.md 记录，不将计划当作已完成结果。
